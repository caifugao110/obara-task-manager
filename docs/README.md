## 3. 文档边界（同一条信息只写一遍）

六份主体文档按「问题类型」分工，不按功能模块分工：

| 你想问的问题 | 该看 |
|-------------|------|
| 这个功能怎么用？为什么我被拦下？ | USER-GUIDE |
| 系统有什么、为什么这样设计、数据怎么存？ | README |
| 这个改动要动哪些文件、要注意什么？ | DEVELOPMENT |
| 这个接口收什么、回什么、谁有权限？ | API |
| 怎么装、怎么备份、挂了怎么救？ | DEPLOYMENT |
| 昨晚后端断过没有？证据在哪？ | TOOLS |

因此：

- 使用手册**不写**接口、表结构、脚本参数；部署指南**不写**业务规则。
- 同一个规则在两处出现时，一处详述、另一处只做一句话摘要并链接过去（例如主页面快捷键在 README 有完整表，使用手册只提最常用的）。
- 新增功能先落 README 的「当前功能」，确认稳定后再同步进使用手册——两边的详细程度不同是**有意的**。

## 4. 一致性自检

文档最容易烂在「代码改了、文档没跟上」。仓库自带零依赖检查脚本，提交前跑一次：

```bat
node tools/docs-check.js
```

它做五件事，任何一项不符就以退出码 1 结束：

| 检查 | 内容 |
|------|------|
| `links` | 所有相对链接指向的文件是否存在、`#锚点` 是否对得上标题（按 GitHub 的 slug 规则，中文标题也能校验） |
| `api` | `backend/routes/*.js` 的真实路由 ↔ `docs/API.md` 记录的端点，**双向**比对（代码多写的、文档多写的都会报） |
| `env` | 后端代码读取的 `process.env.*` 是否都在文档里出现过（`NODE_ENV`、`PORT` 等运行时注入的除外） |
| `pages` | `frontend/src/App.tsx` 的路由是否都写进 README 的「主要页面」表 |
| `paths` | 文档里用反引号标注的仓库路径（如 `backend/routes/tasks.js`、`tools/backend-report.ps1`）是否真的存在——文件被改名或删除时能立刻发现 |

只查某一项：`node tools/docs-check.js links`（可选 `links` / `api` / `env` / `pages` / `paths`），也可以用 `npm run docs:check`。

**它查不出什么**：字段含义写错、示例值与代码不符、判定规则描述过时。这些仍需人工判断——改代码时按 [开发者指南的文档同步表](DEVELOPMENT.md#注释与文档同步) 逐条过。

## 5. 新增或调整文档的约定

1. **先判断是不是新文档**：能并入现有六份主体的，就不要新建——文档数量的成本远高于篇幅。
2. 放在 `docs/` 下，文件名全大写、短横线分词（`API.md`、`USER-GUIDE.md`）。
3. 顶部加一行导航，与其他文档保持一致：
   ```markdown
   > 其他文档：[文档中心](README.md) · [README](../README.md)（功能与使用） · [使用手册](USER-GUIDE.md) · [开发者指南](DEVELOPMENT.md) · [API 文档](API.md) · [部署指南](DEPLOYMENT.md) · [运维工具说明](TOOLS.md)
   ```
4. 超过 100 行的文档必须有「目录」，条目用 `- [标题](#锚点)`，锚点与标题一致（中文标题直接写中文）。
5. 在**本文件第 1 节的清单**和 **README 的「文档导航」表**各补一行——两处都要，缺一处就会有人找不到。
6. 跑 `node tools/docs-check.js`，确认链接与锚点无误。

## 6. 编写风格

- **先结论，后细节**：每个小节第一句回答「这是什么/什么时候用」，再展开。
- 写「为什么」而不只是「是什么」：例如「共享盘读取必须走子进程」要说明不这么做会占满 libuv 线程池、表现是端口在监听但所有请求超时。
- 命令、路径、字段名用反引号；可直接执行的多行命令用代码块并标注语言（`bat` / `bash` / `js` / `json`）。
- 表格优先于长段落：并列的枚举（参数、错误码、脚本）用表格。
- 不写「显然」「简单」「只需」——对读者未必显然。
- 日期写绝对日期（2026-11-09），不写「昨天」「最近」。
